
# GitOps for Grafana and Elasticsearch BAU changes

The k8s-deployer tool offers a practical starting point for moving routine Grafana and Elasticsearch configuration into a GitOps workflow. It runs scheduled scripts from a Git repository inside Kubernetes. Replicas use leader election so only one runs a job at a time. Before each run, the leader pulls the configured branch and executes a snapshot tied to a specific commit. Helm-managed YAML defines the jobs and schedules; the scripts live in Git.

**This pattern addresses a specific operational pressure: a central team is responsible for routine Grafana and Elasticsearch customization, while hundreds of application teams send configuration requests, often by email. A GitOps workflow can make those requests self-service while keeping the central team responsible for the service, guardrails, and exceptions.**

Each use case can have its own configuration repository as its source of truth. An application team could submit a pull request to add or update a Grafana data source or dashboard definition, or to change an Elasticsearch index lifecycle policy. Automated checks could validate structure, naming conventions, ownership, permissions, and other team-defined rules. If all checks pass, the PR could be merged automatically and the scheduled reconciler could apply the change. If a check fails, the workflow can stop the PR and comment with the reason, so the requesting team can correct it without a long email exchange.

**The same pattern can extend to other repeatable cluster operations: define the desired configuration in Git, validate it before merge, and use an idempotent script to reconcile the service. New use cases can be added as separate jobs and repositories, while reusing the scheduler’s execution, logging, and audit mechanisms.**

Audit persistence is important for compliance as well as troubleshooting. With audit enabled, the scheduler can store execution records in PostgreSQL, including the job, script, commit SHA and Git author/committer metadata, execution times, status, exit code, and captured output. That gives the team a durable record linking an operational change to the code revision and its execution outcome. For environments with audit or regulatory requirements, this trail should be part of the design, with appropriate retention, access controls, and database backup policies. The README describes audit persistence as optional and notes that its bundled PostgreSQL is a minimal single-replica deployment, not a high-availability or backup solution; a compliance design should account for those limits.

This supports general DevOps practices: review changes before application, keep configuration versioned, use automated validation, promote consistent definitions across environments, and make rollback possible through Git history. Scripts should be idempotent so rerunning a job safely brings Grafana or Elasticsearch toward the declared state. The scheduler itself is a useful execution foundation, but its cron model is not a full continuous reconciler: it does not catch up missed runs or automatically detect every manual change. The team should choose an appropriate schedule and alert on failed jobs or drift; use an event-driven controller if near-immediate reconciliation is required.

## Security and operational load

A click-ops admin UI would create a privileged write path into Grafana and Elasticsearch. Central-team engineers would need administrative access through the UI, with dedicated authentication, authorization, and RBAC controls. The UI and its integrations would become sensitive components to secure, operate, and audit.

The GitOps flow can keep administrative credentials out of engineers’ routine workflows. Kubernetes service accounts can give the scheduler narrowly scoped access to the cluster, while separate application service accounts or credentials give scripts the permissions they need in Grafana and Elasticsearch. Those credentials can be stored as Kubernetes Secrets and restricted to the relevant workload. Central-team members manage the process through repository policy and guardrails; the pipeline applies approved changes without requiring them to log in and make each change. Exceptional cases can be handled individually outside the routine pipeline.

## Why this scales better than click-ops

A central admin UI could accept requests and trigger scripts, but it would make the UI another system to build and maintain: it needs forms for every configuration type, validation and authorization logic, workflow state, history, and integrations to handle exceptions. As requests and use cases grow, UI behavior and operational dependencies tend to grow with them. Unless the UI also provides a strong reviewable source of truth, it can be hard to reproduce a change, compare environments, or establish exactly what was approved and applied.

In the GitOps model, self-service means application teams express changes through familiar repository workflows rather than waiting for the central team to re-enter requests from email. The central team defines guardrails and handles exceptions; routine, valid changes can flow through automatically. This is management by exception: people focus on failed validations, unusual requests, and operational problems instead of manually processing every routine update.

The approach scales because the same PR checks and reconciliation pattern can serve many teams and configuration types. Git supplies a shared, reviewable history, and the cluster automation applies approved state consistently. A UI could still provide a convenient status view, but treating Git as the source of truth keeps requests, validation results, approvals, and applied configuration connected as the workload grows.
